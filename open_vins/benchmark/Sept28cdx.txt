HW290/OpenVINS hardware repair and ORB-SLAM3 computational optimization

Introduction

The work addressed two objectives: make the rigidly mounted HW290 IMU and ELP
stereo camera produce a realistic OpenVINS trajectory, and reduce ORB-SLAM3
computation while retaining useful visual-inertial trajectory accuracy. The
requested longer-term targets are ORB-SLAM3 using less computation than
OpenVINS and OpenVINS producing the more accurate trajectory. These rankings
must be established by measurements; they have not yet been achieved.

This report records the completed repair and validation work from the ongoing
session, including work begun on 25 September. The dataset trials below have
now completed. Physical movement testing ended with the user's 20 cm test.

Camera and IMU diagnosis

The installed usb_cam 0.8.1 timestamp conversion divided a microsecond field
by 1000 before adding it to a microsecond epoch. This produced a camera/IMU
timing mismatch that changed between camera process starts. The conversion
was corrected in a locally built camera driver. The hardware launchers now
use this driver, with the splitter's arrival-time correction disabled.

The HW290 returned WHO_AM_I 0x98, matching the ICM-20689 register identity,
rather than the MPU6050 previously assumed. This is a register identification,
not independent verification of the chip. Firmware now configures the relevant
accelerometer low-pass filter as well as the gyro filter and sample rate.
After clipping appeared during calibration, the measurement ranges were
changed to +/-4 g and +/-500 degrees/s. Versioned IMU packets select the
correct conversion to acceleration in m/s^2 and angular velocity in rad/s.

Serial-arrival timing was replaced with reconstructed MCU acquisition timing.
Packets include sample sequence numbers and checksums. The bridge retains
partial serial records, handles micros counter wrap, reports dropped packets,
rejects saturation and stops on a clock reset. USB latency uncertainty remains;
this is not a hardware-triggered camera/IMU synchronization system.

An intermittent restart failure was traced to an unsuccessful I2C identity
read. Firmware now clears an interrupted bus transaction, uses 100 kHz I2C,
retries initialization and verifies rate/range registers. Three successive
reconnect checks each produced 235 valid packets without checksum errors.
The subsequent physical movement test also started successfully.

Mount calibration and OpenVINS repair

The user confirmed that the rigid IMU mount had shifted and rotated slightly.
A fresh motion capture was used to estimate rotation and camera/IMU timing.
The calibration helper was corrected to use rectified-camera intrinsics,
rather than applying raw-image distortion to already rectified images.
It also accounts for measured stationary gyro bias and reports a held-out
rotation residual. The capture supplied 247 usable rotation pairs, with a
0.399 degree training median and 0.386 degree held-out median residual.

The updated camera-to-IMU time offset is +0.020 seconds. The earlier +0.155
second value belonged to the old timing setup and is obsolete. The user
measured the IMU approximately 4 cm from both lens centres and supplied
photographs. These were used to replace the zero lever arm with an approximate
nonzero translation. The depth component is estimated from the photos, so
this is not a full translational calibration. Static transforms now come from
the same calibration YAML used by OpenVINS.

An OpenVINS worker callback captured a local timestamp by reference after its
lifetime ended. It now owns the timestamp value, retains its worker threads
and joins them before reuse or destruction. Full EuRoC replays subsequently
completed and shut down normally. Hardware feature-update capacity and camera
tracking frequency were adjusted to avoid unnecessarily discarding available
visual measurements.

Public dataset comparison method

The complete EuRoC V1_01_easy sequence was replayed at normal speed: 2,912
stereo pairs at 20 Hz and 29,120 IMU samples at 200 Hz. Trials ran sequentially
on the Intel N100 four-core host with GUI disabled. Estimator CPU time is user
plus system time from /usr/bin/time -v, including startup and shutdown. Peak
resident memory is reported separately. Replay and sensor-driver costs are
excluded for both systems; these are not whole-hardware-pipeline power tests.
The host was not isolated from every background application, so the numbers
are local process measurements rather than a controlled multi-host study.

Both estimators are compared using online IMU-frame poses against dataset
ground truth. Evaluation uses rigid SE(3) alignment without scale fitting.
The table below uses a common interval beginning 30 seconds after the dataset
camera start, after initial inertial optimization. Whole-interval results are
also saved. One-second relative-pose translation error and pose coverage are
checked alongside absolute trajectory error (ATE).

The ORB baseline uses 1,200 features, default OpenCV threading and loop closure
enabled, with the same repaired ROS wrapper as the candidate trials. Its raw
online trajectory had a large coordinate change during inertial initialization;
whole-interval ATE was about 6.72 m, although post-initialization ATE was about
4 cm. A retrospectively corrected map trajectory does not have the same history.
Consequently, retrospective ORB poses are not mixed with online OpenVINS poses.

ORB uses a best-effort image subscription and delivered fewer poses than
OpenVINS's reliable subscription. Coverage is therefore reported explicitly.
CPU comparisons concern these actual ROS pipelines, not exactly equal numbers
of processed frames. Trial-to-trial variation and additional datasets remain
necessary before claiming a general algorithm ranking.

Implemented ORB changes and rejected settings

The ROS wrapper uses one OpenCV thread by default, shares image storage where
possible, handles IMU callbacks separately, and waits for appropriate IMU
coverage before processing buffered stereo images. Expensive visualization
work is performed only when subscribed and at a reduced publication rate.
The full-rate online IMU pose remains available for trajectory evaluation.
RViz and Pangolin are opt-in rather than default benchmark overhead.

An isolated ORB core variant optionally caps the locally optimized keyframe
window. The 12-keyframe candidate preserves local mapping and global inertial
initialization. The original ORB core library is unchanged, and the isolated
build records source/library hashes and compile/link arguments for reproduction.
Disabling mapping altogether was not used as a shortcut to a misleadingly
cheap result without the required inertial initialization and map refinement.

The installed hardware launcher defaults to 800 features with loop closure off.
Its --efficient option selects 600 features and the isolated core's local BA
cap. These computational settings have dataset evidence; their trajectory
accuracy on the physical HW290 rig has not yet been measured.

A 400-feature ORB trial did not initialize because the upstream stereo
initializer requires more than 500 detected features. It is rejected, not
reported as a low-cost success. Enlarging the OpenVINS tracking/state window
also increased CPU without improving the selected profile's trajectory error.
The smaller fixed-calibration OpenVINS configuration is retained.

Current status and conclusion

The resized ORB trial and its repeat both completed normally. CPU time was
121.91 and 120.49 seconds; post-initialization ATE was 3.11 and 3.18 cm.
One-second relative-pose translation error was 4.55 and 4.60 cm. The selected
OpenVINS profile used 78.70 CPU seconds with 4.09 cm post-initialization ATE
and 4.53 cm relative-pose translation error. The efficient ORB profile remains
about 1.53-1.55 times as expensive in CPU time and over five times as large in
peak resident memory as this OpenVINS profile.

The hardware displacement problem improved substantially in the controlled
20 cm check, and the ORB compute reduction was reproduced on one public
sequence. The requested combination of cheaper ORB and more accurate OpenVINS
is not established by the post-initialization comparison. ORB initialization
coordinate changes and the approximate HW290 translation calibration remain
known limitations. Hardware launch uses native 640x480 rectified camera images;
the EuRoC resize setting is dataset-specific. No additional physical movement
is requested, and the benchmark processes launched for these trials have ended.

Latest launcher behaviour requested by user

RViz now launches even if the IMU fails its startup check. When startup fails,
it opens the sensor-view configuration (fixed frame cam0) so images and rigid
sensor transforms can be inspected. VIO is skipped until the connection is
restored and the launcher restarted. If a sensor fails during operation, VIO
stops but RViz remains open. Ctrl-C or closing RViz ends the run and prints the
resource summary. --no-rviz retains automatic shutdown on a process failure.
Both OpenVINS and ORB launchers use this behaviour. Shell syntax and a process
lifecycle check verified that the viewer survives an early sensor-process exit.
This supersedes the earlier description that a sensor failure closes all nodes.
